Four things the owner named (Banglish), all fixed in **v286 / 3.9.209**:

1. The Android "My code / Scan" switch was still a wide pill hugging the **left**
   edge → it is now a small, **centred**, **nav-bar-like** control at the top.

## 1. The "My code / Scan" switch — centred, small, nav-bar-like

**File:** `native-android/app/src/main/java/app/kuchupuchu/android/QrScreen.kt`

The round-33 control was compact but still sat in the **top-left** corner as a
pill of two 84dp buttons. The owner asked for it to be **centred**, **smaller**,
like a **nav bar**, at the **top** of the screen.

* The switch now lives in a `Box` with `contentAlignment = Alignment.Center`
  and `Modifier.fillMaxWidth()` → it is centred on any width.
* Each tab is an **icon + a label**: `Icons.Filled.QrCode` / `Icons.Filled.QrCodeScanner`,
  15dp icon, 12.5sp label, 14dp/7dp padding — the same language as the app's
  own bottom navigation (icon over/next to a label, the active one filled with
  the accent).
* The active tab is filled with `ActionBlueDeep`; the inactive one is `Muted`.
  The tint animates (`animateColorAsState`, 180 ms) like the nav items do.

## 2. The desktop message bar was cut off — measured, then fixed

**File:** `web/src/styles.css` (+ the new `scripts/measure-desktop-layout.mjs`)

`scripts/measure-desktop-layout.mjs` opens a real conversation in the built web
app (Playwright, 1440×900) and prints the geometry of every box that matters.
Before the fix it said:

```
.workspace            0 → 900   (900)
.conversation-pane    0 → 1097  (1097)   ← taller than the viewport
.transcript          74 → 1022  (948)
.composer           1022 → 1097 (75)     ← CUT OFF by 197px
```

**Root cause:** `.workspace` is a CSS grid with three columns and **one
implicit row**, sized `auto`. An `auto` row is sized by its content, and the
chat pane's content is the transcript — as tall as the whole message list
(410 messages in the test chat). So the row grew to 1097px, the pane grew with
it, and the composer (the last row of the chat) was pushed **below the bottom
of the window**, clipped by `.kp-app { overflow: hidden }` and unreachable. It
only shows up in a chat with a long history — which is exactly where the owner
saw it.

**Fix:** one explicit row, pinned to the viewport height:

```css
.workspace {
  grid-template-rows: minmax(0, 1fr);
}
```

The transcript already carries `flex: 1; min-height: 0`, so it now scrolls
*inside* the pane exactly like the mobile layout does. After the fix:

```
.conversation-pane    0 → 900   (900)    = the viewport
.transcript          74 → 825  (751)    scrolls
.composer           825 → 900  (75)     fully visible
```

Verified at 1440×900, 1920×1080, 1366×768 and 390×844 (mobile: 58px spare
for the bottom nav) — the composer is fully visible in all of them.

## 4. The D1 row-write burn

### What the free tier was actually spending (measured, 24 h)

`npx wrangler d1 insights kuchupuchu-v3-apac --time-period 1d --limit 250
--sort-by writes --sort-type sum` (and the GraphQL
`d1QueriesAdaptiveGroups` / `d1AnalyticsAdaptiveGroups` endpoints) told the
whole story:

| rows written | runs | statement | why it never stopped |
| ---: | ---: | --- | --- |
| **26 522** | 1 495 | `UPDATE messages SET client_id = json_extract(meta_json,'$.clientId') WHERE client_id IS NULL AND meta_json IS NOT NULL` | rows whose `meta_json` has **no** `clientId` make `json_extract` return NULL → the row stays NULL → it is re-written on **every** schema walk |
| **10 224** | 3 408 | `INSERT INTO error_log` | one row per failed request; a D1 write refusal *is* a failed request, so the outage fed itself |
| **3 080** | 1 296 | `UPDATE login_requests SET new_device_platform='WEB' WHERE new_device_id LIKE 'web-%'` | no `platform <> 'WEB'` guard → the same rows are re-written every walk |
| **1 332** | 1 948 | `UPDATE auth_devices SET platform='WEB' WHERE device_id LIKE 'web-%'` | same |
| 142 | 1 281 | `UPDATE recovery_requests SET new_device_platform='WEB' …` | same |
| 284 | 142 | `INSERT OR REPLACE INTO rate_limits` | 1 write per call on 41 call sites, incl. hot read routes |
| 135 | 135 | `INSERT OR REPLACE INTO schema_meta` | the fingerprint write — one per completed walk |
| 92 | 92 | `INSERT INTO metrics_daily` | fine |
| 33 / 33 / 31 / 19 / 11 / 6 | — | `last_active_at`, `members.unread`, `last_read_at`, `auth_devices.last_seen_at`, rate-limit prune, `web_login_sessions` | already throttled, fine |

Total ≈ **42 000 rows/day** of the 100 000/day free cap, and on 2026-10-17 the
first two hours of the day already burned 24 000 of them (06:00 → 13 028 rows,
07:00 → 11 324) — which is why the quota was spent by 08:00 and the whole
product was a 503 for the rest of the day.

### The four fixes (all in `src/worker/index.ts`)

1. **The backfill converges.** `CLIENT_ID_BACKFILL` now carries
   `AND json_extract(meta_json, '$.clientId') IS NOT NULL`. A row is written
   at most once; a message that never had a clientId is left alone instead of
   being re-written on every walk. (26 522 → 0 after the first run.)
2. **The platform backfills converge.** `auth_devices`, `login_requests` and
   `recovery_requests` now guard with
   `AND (<column> IS NULL OR <column> <> 'WEB')`. (4 554 → 0.)
3. **The error log is throttled and quota-aware.** The top-level handler now
   calls `logWorkerError()`: a **D1 quota refusal is never written back into
   D1** (that insert would spend the budget that is already gone and cannot
   succeed anyway), and the same failure is written **at most once a minute
   per isolate**. (10 224 → a handful.)
4. **Only the roomy rate-limit caps are sampled.** `rateLimitGlobal()` used to
   write its counter on every call, so a 600/min route wrote 600 rows a
   minute. The counter is now written on the first hit of a window and then
   every 10th hit — **but only for the round, roomy caps** (60, 90, 120, 300,
   600). The tight caps (8, 10, 20, 30, 40 — the anti-brute-force and
   anti-enumeration limits, e.g. 20 hits per phone number) keep counting
   every single hit, so a 20-hit phone cap does not quietly become a 29-hit
   one. Because the write still happens on every multiple of 10, a round cap
   is reached on exactly the same request as before.

### The schema finally landed

With the quota reset at 00:00 UTC, the missing Phase-R9 DDL was applied by
hand against the production database:

* `ALTER TABLE users ADD COLUMN qr_code TEXT` ✅
* `CREATE TABLE web_login_sessions (...)` ✅
* `CREATE UNIQUE INDEX idx_users_qr_code` ✅ + the expiry index ✅
* `UPDATE users SET qr_code = lower(hex(randomblob(16))) WHERE qr_code IS NULL`
  → all 19 accounts now carry a code ✅

Live proof: `POST https://kuchupuchu-api.kuchupuchu.workers.dev/api/auth/qr/start`
→ **201** with a token (it answered 503 for days), and the phone's "My code"
panel now draws a real QR bitmap instead of spinning.
