# Owner round 33 — 2026-10-18: the QR screen, the hero banner, the back-to-QR button and the country list

Four things the owner named on 2026-10-18 (from the Android QR screen
screenshot and the live web app), plus one thing the round uncovered that
is bigger than all four.

Every item below was **reproduced at the source** before it was changed, and
the fix is pinned by `test/cases/100-qr-screen-and-login-fixes.mjs`.

---

## 1. Android — the QR screen (`QrScreen.kt`)

### 1a. The content was cut off at the bottom

**Cause.** `MyQrPane` was a `Column` with a fixed height and a hard-coded
stack of blocks (avatar 84dp, a 240dp QR panel, two lines of copy, the reset
row, and a second caption under it). On a normal phone that stack is taller
than the window, and a plain `Column` clips the overflow — the last line sat
half-drawn under the navigation bar.

**Fix.** The pane is a `verticalScroll(rememberScrollState())` column now, and
the blocks were tightened (avatar 84→76dp, QR panel 240→216dp, the copy and
the reset row pulled closer together). Nothing is cut off at any screen size.

### 1b. The "My code / Scan" switch was huge

**Cause.** The switch was a `fillMaxWidth()` pill with two `QrTabButton`s at
`Modifier.weight(1f)` and 10dp of vertical padding — a full-width, ~40dp-tall
bar that ate a third of the screen.

**Fix.** A compact segmented control: fixed 84dp-wide tabs, 6dp of vertical
padding, 12.5sp labels, hugging its content in the top-left corner.

### 1c. The QR code had no visible border

**Cause.** The panel's border was `1.dp` of `CircleButtonEdge` — in the
dark-blue theme that is `#3360A5FA`, a 20%-alpha blue. On a white card it is
invisible, so the code looked unframed.

**Fix.** A `2.dp` accent border (`ActionBlueDeep`) around the panel, and the
code itself is drawn at 184dp inside the 216dp panel — the white margin
around it is the QR's quiet zone, without which scanners struggle to lock on.

### 1d. The scanner had no frame, and the phone had to be turned over

**Cause 1 (the frame).** The scanner was the zxing **default** capture
activity. Its `ViewfinderView` paints a translucent mask outside the scan area
and a laser line inside it — **no border at all**. The app's own scan pane was
a bare icon on the page, with nothing that looked like a viewfinder.

**Cause 2 (the turning).** `ScanOptions.setOrientationLocked(false)` told the
library *not* to lock the orientation, so the capture activity followed the
device's rotation. A portrait app therefore handed the camera a sideways
preview and the phone had to be turned over to read a code.

**Fix.**

* `setOrientationLocked(true)` — the scanner stays in the app's orientation.
* `KpScanActivity` (a `CaptureActivity` subclass) replaces the layout with
  `kp_scan_capture.xml`: the same `DecoratedBarcodeView`, plus
  `KpScanFrameView`, which draws the four corner brackets in the app's accent
  blue over the library's own mask. The activity is registered in the manifest
  with `android:screenOrientation="portrait"`.
* The framing rect is pinned to 250dp (`zxing_framing_rect_width/height`) so
  the brackets and the area the decoder actually reads are the same box.
* The scanner's theme (`Theme.KuchuPuchu.Scan`) matches the library's mask,
  laser and result colours to the app's palette.

The app's own scan pane now carries the same accent border as the code panel.

### 1e. The code never appeared at all (found while fixing 1a)

**Symptom.** The screenshot showed the white panel with a spinner that never
stopped — the screen spins for ever when `qrCode` is blank.

**Cause.** `userSelf()` reads `row.qr_code`, and the **production D1 database
has no `qr_code` column at all** (see §5). Every profile therefore carried
`qrCode: null`, and the pane spun for ever.

**Fix (defence in depth).** The pane now mints a code itself when the
account has none (`POST /api/users/me/qr-code/reset` — the same route the
"Reset code" button uses), keeps `Store.me` in step, and — if the server
cannot mint one — says so plainly and offers a **Try again** button instead
of spinning.

### 1f. The junk

The standalone caption "The old code stops working the moment you reset it."
repeated the reset button's own label and pushed the rest of the screen
down. It is gone.

## 2. Web — the banner did not load

**Cause.** `WelcomePage.tsx` pointed its hero image at `/hero-illustration.jpg`.
**That file has never existed** in `web/public/`. The request fell through to
the SPA rewrite, so the server answered **200 with `content-type: text/html`**
(the app shell) — the browser got HTML where it expected a JPEG, and the
banner rendered as an empty frame.

The artwork was sitting in `web/public/` the whole time, named `banner.jpg`
(1600×639, "encrypted chat bubbles and lock shields around a smartphone" —
the very thing the `alt` text describes).

**Fix.** The hero now points at `/banner.jpg`, with the real intrinsic size.
A sweep of every root-relative asset reference in `web/src` confirms that
`/logo.png` and `/banner.jpg` are the only ones, and both exist.

## 3. Web — no way back to the QR login

**Cause.** The QR panel offers "Log in with phone number", but the phone
form had no button to return to the QR code. Once you had gone to the number
form, the QR path was gone for that page load.

**Fix.** `switchToQr()` in `AuthScreen.tsx` and a **"Sign in with a QR code
instead"** button under the phone form. Going back remounts `QrLoginPanel`,
which mints a fresh login token.

## 4. Web — the country dropdown showed nothing

**Cause.** A native `<select>` paints its **option list** with the *system*
list colours, not the page's. On a light-themed phone the list is white while
the option text inherited the field's near-white colour (`#edf3fc` on
`.auth-input`) — **white text on a white list**. The field itself looked
fine; the list was unreadable.

**Fix.** The field carries `.auth-select`, which declares
`color-scheme: dark` (so the browser paints the popup dark) and gives the
`option`/`optgroup` elements the card's own colours
(`background-color: #0f182a; color: #edf3fc`).

## 5. The bigger one: production has no QR schema at all

While reproducing 1e, the D1 database was queried directly:

```
$ wrangler d1 execute kuchupuchu-v3-apac --remote \
    --command "SELECT id, display_name, qr_code FROM users LIMIT 8"
no such column: qr_code

$ ... --command "SELECT ... FROM web_login_sessions"
no such table: web_login_sessions
```

The **production** database is missing both pieces of the phase-R9 QR
schema:

| object | state in production |
| --- | --- |
| `users.qr_code` column | **missing** |
| `idx_users_qr_code` index | **missing** |
| `web_login_sessions` table | **missing** |
| `idx_web_login_sessions_expiry` index | **missing** |

Everything else (including the later R2 identity-link and classroom tables)
is present, so the schema walk last completed **before** phase R9 landed.

**Cause.** The D1 account is on the Workers Free plan, whose daily row-write
limit is 100 000 rows. `ensureSchema()` runs the DDL as one batch and then
the migrations; the batch is **refused outright** once the budget is gone
(`Your account has exceeded D1's free tier daily row write limit…`), the walk
is blocked, and the fingerprint is never written — so the next cold isolate
walks again and is refused again. The budget is gone **every day**: the
write limit is reached in the evening and the writes (and the schema) stay
refused until 00:00 UTC.

**Consequence.** On production today:

* the phone's "My code" panel has no code to draw (fixed in the app above —
  it now mints one, but the mint is a write, so it also needs the budget);
* `POST /api/auth/qr/start` (the web QR login) answers **503 BUSY**;
* every write route (sign-in, messages, receipts) is refused for the rest of
  the UTC day.

**What actually fixes it:** a paid Cloudflare plan (the ceiling disappears),
or a write-budget diet. Until then, the schema lands by itself within a few
minutes of the 00:00 UTC reset — the walk retries every 5 minutes — but the
budget is normally spent again before the next day ends, so the QR features
keep flickering.
